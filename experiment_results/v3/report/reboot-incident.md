# 正式 v3 実験中の Mac 再起動

## 概要

2026-10-24 12:19:50 JST に Mac が再起動した。正式 v3 の runner と測定中の子プロセスが消失し、実験が中断した。**再起動の原因は未特定**であり、GPU lock の停止、OS panic、メモリ不足又は手動再起動のいずれかに分類できる直接証拠は得られていない。

## 実験への影響

中断後の `raw/results.jsonl` と `checkpoint.json` は 1,074 / 3,210 条件で一致した。内訳は success 1,000、memory_limit 6、timeout 3、warmup_failed 20、unavailable 45。最後の確定条件は `v3-basic-web-NotreDame-rr_sparse_sgd-s2-p200-tNone` である。

次の `web-NotreDame / Sparse CPU / seed 3 / P=200` は結果確定前に中断しており、その途中試行を成功・失敗のいずれにも算入しない。確定済み 1,074 条件を保持し、未確定の途中成果物は再実行と混在しない場所へ退避してから、同じ実行ファイル・入力・制限のまま 12:24 頃に再開した。OS 再起動前後のシステム状態は同一ではないため、この境界を記録に残す。

## 軽量調査で確認したこと

- `sysctl kern.boottime` は `sec = 1792811990, usec = 899096`、すなわち 2026-10-24 12:19:50 JST を返した。runner のみの停止ではなく OS の起動し直しがあったことを確認した。
- システムとユーザーの DiagnosticReports（Retired を含む）のファイル名と更新日時を確認したが、この再起動時刻に対応する panic / watchdog / shutdown 診断ファイルは見つからなかった。見つからないことは、panic がなかったことの証明ではない。
- 起動直後に作成された Code と Autoupdate の診断は、各々 12:20:12 / 12:20:45 の **disk writes** イベントだった。再起動原因を示す診断としては扱わない。
- 起動前後を対象に、shutdown cause、panic、shutdown/reboot プロセス、loginwindow の restart/shutdown を限定検索した。取得できた範囲には panic 本文や再起動理由の明示はなく、起動後の一般的な panic 関連クラスの登録・アプリ復元ログのみだった。`panic` という単語を含む通常ログを panic 発生と誤認しない。
- 同日 00:45 の JetsamEvent は見つかったが、今回の再起動とは約 11 時間半離れており、今回の原因に結び付ける証拠はない。

調査はファイル名・診断のイベント種別と限定 OS ログの読み取りだけで行った。コンパイル、追加測定、プロセス停止、OS 設定変更は行っていない。個人情報を含み得る全システムログは成果物に保存していない。

## 解釈の限界

直前の複数手法の遅延と、11:49 の swap / 圧縮メモリのスナップショットは [別調査](web-notredame-timeout-system-snapshot.md) に記録した。ただし、遅延時点の同時計測でも、再起動直前の計測でもない。遅延・メモリ状態・再起動の因果関係は断定できない。CPU 実行中に再起動したという事実だけから、CPU 実装又は GPU lock を原因とすることもできない。

本事故は「ホスト再起動による測定中断」として報告し、確定済みの通常 timeout / RSS 停止とは区別する。再起動前の OS 状態・温度・電源・操作履歴の連続記録がないため、今回の証拠だけで原因を絞り込むことはできない。

### 入力・乱数に関係する来歴の照合

- 全 9 組で、入力 SHA、手法別 binary SHA、seed、15 反復、epsilon=0.1、P=200 が一致した。
- basic と convergence の両方が成功した 6 組（seed 0 の全手法、seed 1 の CPU / RR、seed 2 の RR）は、初期配置 SHA、共通前処理 SHA、制約数も一致した。stress 定義も sampled / 256 sources / stress seed 0 で一致した。
- basic の timeout 3 条件は native 結果 JSON を出す前に停止しており、初期配置 SHA・前処理 SHA・制約数・実際の stress 評価 metadata は欠測である。両 command の stress source 数指定は 256 で一致するが、欠測値を「実測一致」とは扱わない。
- No.5 内では各 seed の 3 手法で入力・初期配置・前処理 SHA と制約数が一致した。制約数は seed 0 が 66,214,926、seed 1 が 66,215,122、seed 2 が 66,214,524 で、以前成功した同 seed の CPU / RR 記録とも一致する。
- CPU seed 1 の最終 stress は、遅かった basic と今回の convergence の両方で **7,311,566,741.47717** と完全に一致した。CPU seed 0 と RR seed 0 / 1 / 2 の最終 stress も JSON 値が一致した。これは記録された最終 stress 値の一致であり、今回は座標を読んで一致を確認したという意味ではない。

照合できた成功例について、別の入力や初期乱数系列へ変わったことを以前の遅延の説明とする根拠は得られなかった。同じ seed 1 / 2 でも後続の収束計測では全手法が完走しており、「その seed では常に 120 秒以内に終わらない」という説明には合わない。一方、以前 timeout した実行の内部状態は部分欠測であり、全失敗例の乱数状態が正しかったことまで証明したわけではない。Atomic seed 0 の最終 stress は両計測で異なり、完了数だけから更新順序・同期の内部原因や実装の正しさを確定することもできない。

### 比較の制限

**basic と convergence は計測付加が同一ではない。** basic は毎反復の時間 trace のみ、convergence は反復 0 / 1 / 2 / 3 / 5 / 8 / 10 / 15 で座標 checkpoint の保存を追加する。No.5 の記録済み trace copy / IO overhead は約 0.035〜0.049 秒で、表の SGD 区間からは除外するが、保存・readback が実行状態へ与える影響まで消せるわけではない。全体秒にはその保存が含まれる。

同じ seed の比較証拠は増えたが、実行時刻・システム状態・checkpoint 設定が異なるため、厳密な再現対照実験や再起動だけの介入効果とは解釈しない。以前の timeout 3 件と遅延した成功値を保持し、今回の成功値へ置き換えない。ホスト状態や共有資源の影響という調査候補を支持する範囲に留め、内部原因を特定したとは報告しない。
