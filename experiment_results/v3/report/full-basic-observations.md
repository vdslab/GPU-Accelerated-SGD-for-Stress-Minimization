# No.2 Full20：basic 確定データからの考察メモ

対象は v3 の `study=basic`、Full CPU (`sgd`)・Full Atomic GPU (`atomic_sgd`)・Full RR GPU (`rr_sgd`) のみ。後続の収束実験・タイル感度実験や、v3 全体の途中進捗を混ぜていない。`raw/results.jsonl` と `config/datasets.json` の軽量読み取りだけで集計し、座標・画像・距離行列は読み込んでいない。

## 集計条件と比較可能数

- 20グラフ × 3法 × seed 0〜4 = 300条件が一意に記録済み。成功289、`memory_limit` 6、`warmup_failed` 5。CPU成功95、Atomic成功95、RR成功99。
- 同 seed のCPU/GPUが両方成功し、グラフ・Full系統・15反復・epsilon 0.1・pivots・入力SHA・初期座標SHA・前処理SHA・ストレスの種類/サンプル数/評価seedが一致するペアだけを使った。成功候補190ペアに不一致なし。各GPU法とも19/20グラフ、95ペアが比較可能で、19グラフすべて5/5ペア。
- 速度比は各seedの `CPU iteration_time_ms / GPU iteration_time_ms`、ストレス比は各seedの `GPU stress_value / CPU stress_value`。表はそれぞれ **対応seed比の中央値［最小, 最大］**。時間やストレスを種間で平均してから割っていない。速度比>1はGPUが速く、ストレス比>1はGPUが悪い。
- 時間は記録済みの15反復のSGD区間合計（トレースのコピー/IOを除外）で、プロセス全体の時間や前処理込みの時間ではない。RRは全条件 T=1024、workgroup=1024。
- ストレス評価は n≤8000 が exact、n>8000 が共通256 source・評価seed 0の sampled。比較可能19グラフのうち16はexact、3はsampled。Full SGDが全ペア制約を使うことと、最終ストレスの評価方法は別。
- 成功289件の native commit はすべて `118d3ec22b350fcc7522527154f3d03131215a25`。

## 結果に基づく短い考察

1. **RRは比較可能19グラフすべてで対応seed速度比の中央値が1を超えるが、品質は一様に保たれない。** 対応seed速度比のグラフ別中央値は1.025〜15.017倍。ストレス比中央値は0.954〜1.671倍で、19中9グラフが1.05超、7グラフが1.10超、4グラフが1.20超。最速条件だけを選ぶと、品質劣化を見落とす。
2. **速度と品質の両立例は bcspwr10、USpowerGrid、fe_4elt2。** RRの速度比中央値 / ストレス比中央値は、それぞれ9.844倍 / 1.00135、7.384倍 / 1.01945、14.955倍 / 1.01699。bcspwr10は5 seedのストレス比が1.00125〜1.00178と狭い。一方、dwt_2680の中央値は4.246倍 / 1.00359だが、ストレス比の幅は0.81813〜1.00787なので、中央値だけではseedごとの差を隠す。
3. **速いが悪化する具体例は wiki-Vote、p2p-Gnutella08、ca-HepTh。** RRはそれぞれ11.646倍 / ストレス1.671倍、9.280倍 / 1.453倍、15.017倍 / 1.328倍。wiki-VoteのRRストレス比は全5 seedで1.573〜1.896倍であり、単独seedの外れ値だけではない。Atomicもwiki-Voteは2.975倍 / 2.269倍、bcsstk17は3.365倍 / 2.921倍となり、速度向上をそのまま改善とは扱えない。
4. **uk のRRは中央値が良くても大きな外れ値が残る。** RRストレス比中央値は1.01383だが、seed 0はCPUストレス127,016.09に対してRR383,893.25で3.02240倍（SGDは2.993秒→0.374秒、8.01060倍）。他seedの比は0.99257〜1.08204。seed 0も入力・初期座標・評価定義は一致する。RRのnative出力 `raw/artifacts/v3-basic-uk-rr_sgd-s0-pNone-t1024/stdout.json` には、`constraints=11,633,076`、`iterations=15`、`attempted_updates=174,496,140`、`completed_updates=174,496,140` がnullでない数値として記録されており、集約JSONでも一致する。RRの `retry_failures` はnullで、Atomicの失敗カウンタ0とは別の情報である。RRメタデータ上の予定・完了数の一致は確認できるが、この読み取りだけで実更新の個別監査・数値的正しさや局所解の原因を証明したとはいえない。
5. **小規模ではAtomicの速度優位がない。** 頂点数1,005〜2,851の6グラフではAtomic速度比中央値が0.064〜0.547倍でCPUより遅い。3,942頂点のbcsstk15で1.002倍とほぼ同速になり、bcsstk15を含む比較可能な3,942頂点以上の13グラフでは速度比中央値が1を超える。ただし頂点数だけで品質は説明できない。例えば約4,800頂点の uk / USpowerGrid はAtomicストレス比1.069 / 1.039倍だが、bcsstk16は1.479倍。グラフ構造・実装費用・更新順等が混在する観測で、頂点数による因果効果とはいわない。
6. **RRにも小規模の例外がある。** 1138_busは中央値1.025倍だが、seed 0は0.774倍、polblogsも中央値1.238倍に対してseed 0は0.746倍。全seedで必ず高速という意味ではない。bcsstk16ではRRストレス比中央値0.95442（4.56%改善）だが、範囲0.93655〜1.03107であり、全seed改善でもない。

## 時間指標を変えた比較（同じ成功集合）

上表と同じ設定・SHA・評価定義の合う **各GPU法95ペア・19グラフ** に限定した追加集計。各グラフで同seedのCPU/GPU比5件の中央値を求め、次にその19個をグラフ等重みで中央値にした。95ペアを直接プールした中央値、全時間の総和の比、時間の平均同士の比ではない。表の括弧内はグラフ別中央値の最小〜最大。

| 手法 | SGD比：グラフ等重み中央値［範囲］ | coldアルゴリズム比：同左 | process wall比：同左 | 追加欠損ペア SGD / cold / wall |
|---|---:|---:|---:|---|
| Full Atomic GPU | 1.298 [0.064, 3.365] | 1.230 [0.075, 2.748] | 1.155 [0.163, 2.660] | 0 / 0 / 0 |
| Full RR GPU | 7.384 [1.025, 15.017] | 3.769 [0.871, 6.390] | 2.597 [0.497, 5.881] | 0 / 0 / 0 |

- **RRのSGD比7.384倍は、cold比3.769倍、wall比2.597倍とは異なる。** 19グラフすべて同じ5ペアを用い、追加欠損はどの指標も0件なので、この差は比較対象集合の変化によるものではない。全工程が7.384倍になったとは書かない。AtomicもSGD比1.298倍に対し、cold比1.230倍、wall比1.155倍だった。
- 例としてfe_4elt2のRRはSGD / cold / wallの対応seed比中央値が14.955 / 6.390 / 5.881倍、wiki-Voteは11.646 / 3.769 / 2.649倍。小さい1138_busは1.025 / 0.871 / 0.497倍であり、SGDではわずかに速くてもcoldやwallでは遅い。dwt_1005も2.103 / 1.257 / 0.991倍で、wallの中央値ではほぼ同速だった。
- `iteration_time_ms` は15反復のSGD処理区間合計。CPUの反復前ペアcloneなど、SGD区間外にも反復関連の費用があるため、SGD比だけではそれらを含む実行全体を評価できない。
- `algorithm_time_cold_ms` は前処理・手法の準備・ランタイム初期化・転送・SGD・読み戻し等を含むアルゴリズム区間で、入力読込・最終stress評価・テキスト出力は除く。新プロセスでの区間名であり、OS/GPUキャッシュが完全にcoldである保証ではない。
- `process_wall_seconds` はnative子プロセス全体の実時間で、入力読込・最終stress評価・座標等の出力も含む。native終了後に行うlossless gzip圧縮と検証は、SGD / cold / wallのいずれにも含めず `archive_seconds` で別記録される。
- これらは異なる区間の測定値であり、比の差をすべてGPU初期化、lock、IO、あるいはCPU cloneだけの寄与と決めない。各成分の区間差と、現在のFull Atomicの監査用記録等の実装差を踏まえて読む。delaunay_n14のCPU欠測はこの追加集計でも救済せず、RR成功4件も比較に追加しない。

## 欠測と解釈上の制限

- **delaunay_n14（16,384頂点）だけは対応CPU結果がない。** CPUはseed 0〜4の5実行がすべて `memory_limit`。Atomicの5条件は `warmup_failed` で、正式な5 seedを実行した失敗ではない。RRはseed 0が `memory_limit`、seed 1〜4は成功だが、同seed CPUがないため速度比・ストレス比には入れない。300条件の記録数と、実際に起動した測定回数は同じではない。
- RRのdelaunay_n14成功4件はSGD 1.549〜1.603秒、ストレス11,239,827.11〜11,746,702.05（256 source）だった。これはRRの絶対値としてのみ参照でき、CPUに対する優劣は評価不可。
- 成功したAtomic 95件すべてで attempted_updates = completed_updates、retry_failures = 0。成功したRR 99件では、attempted_updates と completed_updates は両方nullでない数値であり、いずれも constraints × iterations に一致する。一方、RRの retry_failures は99件すべてnull。したがってRRについて確認したのは予定・完了数のメタデータ一致であり、Atomicのロック失敗検出と同じ監査を通過したという意味ではない。いずれも競合処理・浮動小数演算・更新順序の正しさを全面的に検証した証拠ではない。
- 本メモは固定seedを各1回ずつ測った5 seed比較であり、**同seedの再実行間の分散**は測っていない。Atomicの非決定性の大きさ、悪化を起こす最初の更新、ロック実装の誤りの有無はこの表だけから結論できない。
- 品質差を更新順だけに帰すことはできない。現在のFull Atomic実装・CPU/GPU精度差・計測用記録などの実装差は、別の implementation-scope.md に明記した上でesaに掲載する。
- 表の範囲は5 seedの観測最小最大であり、信頼区間ではない。最大の16,384頂点がCPUの資源制限で欠測しているため、成功した範囲のサイズ傾向を全20やさらに大きなグラフへ一般化しない。
