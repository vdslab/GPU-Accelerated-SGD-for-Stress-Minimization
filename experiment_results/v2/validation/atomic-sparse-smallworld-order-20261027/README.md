# smallworld：同期修正後のstress悪化の切り分け（2026-10-27）

結論：同じseedのpivot不一致は除外できる。同期修正後の座標更新の不整合は今回の検査では見つからず、競合で制約を後回しにする順序の偏りが主因と判断する。同期を維持して同じシャッフル列を小分けに実行すると、品質はCPU付近まで戻った。同期修正を撤回する根拠にはならない。

## 入力と比較条件

smallworld、seed=0、200 pivots、15 iterations、epsilon=0.1。前回のseed 0/1/2計15実行と今回のseed 0反復6実行について、同じseed内の初期配置・入力・前処理SHA-256の一致を再確認した。前処理ハッシュには順序付きpivot一覧、全制約の両端・目標距離・両方向重み、全学習率を含む。異なるseed同士ではpivotは異なるが、修正前後の同じseedでは同じ。

今回の制御実験は同じ前処理後RNGから同じインデックス列を毎回シャッフルする。変更するのはフェンスの有無、または一度に投入する連続部分列の大きさ。全制約を各反復で必ず1回ずつ完了する。分割内では再試行による順序変化があり、CPU順の厳密な再生ではない。stressは全て共通4096始点、評価seed=20261027（小さいほど良い）。

## 実行順序を制御した比較

| GPU投入方式 | 同期修正前 stress / 10⁹ | 同期修正後 stress / 10⁹ |
|---|---:|---:|
| 全20,477,886件を一括 | 0.986869 | 1.106537 |
| 65,536件ずつ | 0.980140 | 0.982725 |
| 16,384件ずつ | 0.984667 | 0.974902 |

参考：同じseedの既存CPU結果は **0.976738 × 10⁹**。各セルは1実行。分割結果だけで性能保証や統計的同等性を主張するものではないが、大幅な悪化が同期を維持したまま解消することを確認した。診断ホストの時間には追加集計を含むため本番の速度比較には使わない。

## 同一seedでも実行ごとに変わる

本番バイナリを交互の順番で3回ずつ実行した。共通4096始点評価：

| 反復 | 修正前 / 10⁹ | 修正後 / 10⁹ |
|---|---:|---:|
| 1 | 1.002117 | 1.010690 |
| 2 | 0.986980 | 1.100511 |
| 3 | 1.003134 | 1.092612 |

前回seed 0の同期修正後は1.230618 × 10⁹だった。固定seedはpivot・初期配置・CPUのシャッフル列を固定するが、GPUのロック獲得順は固定しない。前回の3seed平均「12.7%悪化」はその実行群の観測値であり、普遍的な修正効果として扱わない。64始点評価では今回の修正前の揺れも小さく見えたが、4096始点では0.987～1.003 × 10⁹であり、完全に一定ではない。

## なぜsmallworldで起きるか

入力ファイルの説明では、10万頂点・50万辺のリングを確率0.2でrewireしたWatts–Strogatz型。実データは100,000頂点・499,998辺、次数の平均9.99996、中央値10、最大17。だがSparseの制約数は20,477,886本、制約次数の中央値210、最大99,999。片側のみ更新する制約は19,957,988本（97.46%）。元グラフの低次数だけではGPUロック競合の少なさを推定できない。

片側の重みが0でも両端をロックするので、読み取り側のpivotに制約が集中する。128回の取得試行で失敗した制約は現在のdispatchから抜け、他の制約が終わった後で再投入される。CPUで一様にシャッフルした入力でも、成功した更新順は一様とは限らない。フェンス追加によるクリティカルセクションの長さ・スケジューリングの変化が、この偏りを増やすと考えられる。

追跡なしの診断ホストで、非辺制約の平均再試行pass（最初のdispatch=0）は修正前0.004852、修正後0.011753で **2.42倍**。通常辺はそれぞれ0.0000151、0.0000380。非辺制約が選択的に後回しになることを観測した。ただしこれは総順序の記録ではなく、同一dispatch内の順序も変わる。小分けは後回しになる範囲を制限する。再試行回数だけとstressが単調に対応するとは主張しない。

## 座標の整合性検査

同期修正後・全件投入の別実行で、各制約について両端ロック中に前の更新IDと読み込み前／書き込み後の座標を記録。各反復後、全頂点の履歴を検証した。

- 15反復、307,168,290更新すべて完了。
- 1,228,673,160座標読み込みを直前の書き込みとbit単位比較：不一致0。
- 各頂点の履歴の循環・欠落、最終GPU座標と最後の記録の不一致：0。
- 同じf32入力から独立にf64で更新式を計算：許容値2×10⁻⁵に対して最大スケール化誤差5.51×10⁻⁷、逸脱0。Metalの演算をbit単位で再生した検査ではない。
- dwt_419の正常ログが通り、読み込み記録を意図的に1箇所壊した負の対照が失敗することも確認。

この履歴整合性を通過した追跡実行のstressは **2.095187 × 10⁹** とさらに悪い。大きなstressは、座標の読み書きの不整合がなくても生じる。追跡は追加atomicとメモリ書き込みで実行順序・コンパイラのコード生成に影響し、元の未計測実行の完全再現ではない。そのため未計測の全実行に不具合がないことの証明とはしない。一方で、追跡なしの分割実験も同じ方向の証拠である。

## 判断と次の修正候補

1. pivot不一致：除外。
2. 同期修正が計算式や制約を変えた：該当なし。今回、更新式・読み書き履歴の異常は未検出。
3. 競合依存の更新順序と再試行の偏り：有力な主因。同期を維持した順序介入で大幅悪化を解消した。
4. 元のatomic sparseにもある課題：CPU shuffleありを「CPUと同じランダム更新順」と扱えない。修正前のメモリ同期も不十分だったため、修正前の品質の良さは正当性の証拠にならない。
5. 既存CPU Sparseについて、今回新たな数式バグは見つかっていない。15反復の非凸最適化なので順序への感度はあるが、これだけでCPU実装の不具合とは言えない。

本番の同期フェンスは維持し、シャッフル済み列の一定範囲ごとの完了、競合制約の公平な再投入などを次の候補にする。今回の分割値は切り分け用であり、本番の最適値として採用していない。今回の追加変更は診断ツールのみ。pushなし。
