# wiki-Vote：CPUシャッフル先行生成の比較

確認日：2026-11-05。分割なし（phase_chunks=1）。これは実測結果。本番の既定実装は変更していない。

## 結論

全反復の処理順をCPUの別スレッドで先行生成でき、全60実行で元の本番実装と最終座標のf32ビット列が一致した。正式測定25組中16組で短縮し、同seed・同repetitionの対応差の中央値は **−3.084 ms（対応変化率中央値−1.179%）**。ただし単独に集計した各方式の中央値は **268.256 → 270.800 ms** で逆方向になり、差のばらつきが大きい。今回の試行だけで安定した高速化が得られたとは断定しない。

現行のシャッフル実作業は15反復合計で約1.972 ms、SGD＋読戻し約268 msの約0.74%。重ねる対象自体が小さい。CPUの仕事量が減る変更ではなく、GPU計算中に先行して完了させる変更。

## 条件

- wiki-Voteの無向・単純・最大連結成分：7,066頂点、100,736辺。入力SHA-256：`0efd8c4218dc5ecd45f05d9869144f718416a5db8e9aa4f7fd20de2f51d056e3`。
- Apple M4 Pro、24 GiB、macOS 15.7.2、Metal。T=W=1024、shared、15反復、epsilon=0.1、外側・内側shuffleあり、分割なし。
- 初期配置seed 0〜4。各seedで両方式1回ずつのウォームアップを除外し、その後5回ずつ。正式25対応組／50実行。方式順はseed・repetitionで交互に変更。GPU計算を行う2方式を同時実行しない。
- 同一の入力・初期座標・学習率・処理順・WG内barrier・外側dispatch間依存・反復末尾のGPU完了待ち。trace無効。

## 変更内容

現行方式はCPUが反復開始時に外側・内側の順列を生成し、GPUへ投入し、反復末尾で待つ。比較用の先行方式は、計測開始後にCPUワーカースレッドを起動し、同じseed・同じ乱数消費順で全反復分の順列を生成する。順列を所有権付きでchannelへ渡し、GPU投入側は必要な反復の順列を受け取る。GPUバッファの操作は投入側だけが行い、生成側はGPUに触れない。

ワーカーは生成可能な限り最終反復まで先行する。外側ラウンドの順列状態も引き継ぐため、毎回ID昇順へリセットする変更は入れていない。シェーダーは本番のコピーとSHA一致。

## 計測の境界

SGD計測はCPUワーカー起動より前から開始し、全順列生成・channel待ち・GPU投入・全反復完了・ワーカーjoinを含む。`sgd_to_cpu_ms`にはさらに最終座標のreadback、CPU上での最終座標Vec構築を含める。シャッフルを計測外へ逃がしていない。

最短路計算・初期配置生成・入力読込み・GPUコンテキスト作成はこのSGD計測の前。GPUバッファ準備等は別列。`execute_wall_ms`はバッファ準備・SGD・読戻し・関数終了処理を含むが、前処理、入力パラメータのコピー、コンテキスト生成は除く。これを入力読込みからのプロセス総時間と呼ばない。

`shuffle_cpu_ms`は順列を実際に作った時間の合計で、GPU計算と重なりうる。`plan_wait_ms`はGPU投入側がchannelで順列到着を待った時間。各項は並行するため単純加算しない。GPU timestampの値は反復の最初〜最後のdispatchの時間幅を合計したもので、dispatch間の隙間も含み、純粋な算術処理時間ではない。

## 結果

以下は各方式25実行の中央値。

|計測範囲|現行方式 ms|先行方式 ms|
|---|---:|---:|
|15反復のSGD合計|266.926|269.453|
|1反復平均（合計/15）|17.795|17.964|
|SGD開始〜最終座標のCPU取得|268.256|270.800|
|最終座標の読戻し|1.331|1.336|
|CPUシャッフル実作業の合計|1.972|2.013|
|処理順を待つCPU時間|0.000|0.163|
|GPUバッファ準備等|158.714|164.197|
|execute_sgd呼出し全体|453.249|457.141|

同seed・同repetitionで組にしてから差を計算すると、SGD＋読戻しの対応差中央値は−3.084 ms、対応変化率中央値は−1.179%、速度比中央値は1.012倍。差の範囲は−83.479〜+24.241 ms。**中央値同士の差と、対応差の中央値は同じ統計量ではない。** −83 msのような差を、約2 msのシャッフルだけで説明しない。外れた値も削除せず図と生記録へ残す。

先行方式では、最終反復の順列まで生成完了した時刻の中央値が **計測開始2.062 ms後**。反復1のGPU完了待ちが終わった時刻は中央値37.067 ms後。正式25実行すべてで最終反復の順列が反復1終了より前に完成した。これはホスト側の時刻であり、CPU/GPUの各命令を厳密に同一タイムラインへプロファイルした値ではない。

## 正しさの確認

各seedで変更前の本番`execute_sgd`（phase_chunks=1）も別に実行し、比較用の両方式がその最終座標SHA-256と一致することをassertした。ウォームアップを含む60実行すべて一致。したがってこの入力・5seedでは品質を変えて速度を稼いでいない。Stressの再計算は行っていないが、同じ座標列なので同じ評価条件でのStressは同じになる。

## 解釈と限界

- CPU先行生成という設計は動作し、座標結果も維持できた。
- このwiki-Vote・T=1024条件では、重ねられるシャッフルは元々約2 msしかない。初回channel待ち・スレッド起動・データ受け渡しにも費用がかかる。
- 対応比較では小さな改善傾向がある一方、各方式の中央値では逆方向。GPU timestampの中央値も232.479→233.581 msと揺れており、今回の差をシャッフルだけの効果と断定できない。原因を熱・OS負荷などに特定する測定はしていない。
- 1機種・1グラフ・1回の測定セッション。安定した短縮や他のグラフでの効果は未確認。今回の結果を理由に本番の既定値は変更しない。
